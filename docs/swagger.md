# Правила документации Swagger

Swagger UI доступен по `/docs`, спецификация — `/v3/api-docs` и `/v3/api-docs.yaml`.
Источники документации — аннотации контроллеров и DTO, конфигурация `SwaggerConfig`.

## Язык и стиль

- Названия и описания групп, операций, параметров, полей и ответов пишем на русском.
- Краткое название операции начинаем с глагола: «Создать коробку», «Получить профиль».
- В описании объясняем назначение, условия доступа, ограничения, последствия и поведение повторного запроса.
- Имена JSON-полей, адреса, параметры, значения перечислений и машинные коды сохраняем в формате API.
- Каталог названий и описаний групп находится в `SwaggerTags`. Контроллер ссылается на константу группы; повторять описание в контроллере не нужно.

## Запросы и модели

Каждый публичный параметр и поле, включая поля вложенных объектов и элементов массивов, получает русское описание.
Для параметров контроллера используем `@Parameter`, для полей DTO — `@Schema`, для массивов — `@ArraySchema` с `arraySchema`.
Служебные признаки присутствия полей и методы проверки в DTO не должны появляться в схеме.

Ограничения и обязательность должны соответствовать действующим проверкам API. Не добавляем Bean Validation ради документации.
Указываем единицы измерения, реальные значения по умолчанию и различия между отсутствием поля, `null`, пустой строкой и пустым списком, когда они влияют на поведение.
Для частичного обновления сверяем описание с сеттерами и сервисом.
Примеры должны соответствовать типу, формату и ограничениям поля.
Время указываем в UTC, дату со временем — в ISO 8601, календарную дату — `YYYY-MM-DD`.

Защищённые операции используют `@SecurityRequirement(name = "jwtAuth")`.
Регистрация, вход и операции с токеном обновления не требуют токена доступа.
Если один адрес принимает JSON и multipart, в сгенерированной спецификации должны присутствовать оба типа содержимого.

## Ответы и ошибки

Для каждого ответа указываем фактический HTTP-статус и русское пояснение.
Для `204` используем пустой `@Content`: тела ответа нет.
Для страниц сохраняем конкретный тип элементов `PageResponse<T>`.

Ошибки описываем в формате `CODE: Русское пояснение`.
Несколько кодов одного статуса разделяем точкой с запятой:

```text
INVALID_REQUEST_BODY: Некорректный JSON; INVALID_REQUEST_PARAMETER: Некорректный UUID
```

Код пишем на английском в формате `UPPER_SNAKE_CASE` и сверяем с `GlobalExceptionHandler`, конфигурацией безопасности и ML-обработчиками.
Например, отсутствие вещи возвращает `NOT_FOUND`, а не выдуманный `ITEM_NOT_FOUND`.
Документируем только ошибки, применимые к конкретной операции: конфликт изменения не относится к чтению, а список личных наборов не возвращает ошибку отсутствующего набора.
Ответы с телом ошибки используют `ErrorResponse` и тип `application/json`.

`SwaggerErrorExamples` добавляет примеры известных ответов по документированным кодам.
Пояснение примера русское; `message` и `fieldErrors[].issue` воспроизводят сообщения сервера без перевода.
Примеры ошибок проверки DTO должны ссылаться на реально проверяемые поля и сообщения.
Изменение документации не должно менять реальные коды, сообщения или HTTP-статусы API.

## Проверка изменений

```bash
./mvnw test
./mvnw verify
```

Интеграционные тесты требуют Docker для PostgreSQL через Testcontainers либо настроенную внешнюю тестовую БД, как описано в `TESTING.md`.
`OpenApiDocumentationIntegrationTest` проверяет сгенерированную спецификацию: русский текст, каталог групп, поля моделей, параметры, ошибки, JWT, пагинацию и оба формата планирования упаковки.
Полученная при проверке спецификация сохраняется в `target/openapi-documentation.json` для просмотра.
После изменения аннотаций проверяем `/docs`: группы, вложенные модели, примеры ошибок и переключение типов содержимого.
