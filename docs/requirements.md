# Реализация требований

Основная аудитория — компании, которые перевозят офисы и отделы. Сотрудники описывают коробки, перевозчики отмечают погрузку и доставку, координатор контролирует общий прогресс.

Основание — ТЗ «MoverMate — переезд без хаоса», §4–8. Первый день ведётся обычными задачами; памятки реализованы в мобильном приложении.

## Основные сценарии

| Требование ТЗ | Реализация backend |
| --- | --- |
| §5.1. Проект и готовый план (F-01–F-03) | Название, дата/время, необязательные адреса. Проект, участники, папки и выбранные наборы задач создаются одной транзакцией. Без явного выбора задач план пустой. Личные наборы содержат задачи любых этапов, принадлежат аккаунту и доступны с разных устройств. Общие и свои одиночные образцы можно применять через `/api/task-templates`; изменение образца не меняет созданные задачи, повторное применение даёт 409. |
| §5.1. Свои задачи, сроки и выполнение (F-04–F-06) | Создание, редактирование, удаление, фильтры по этапу и выполнению. Срок FIXED или RELATIVE со смещением в днях; без срока — FIXED с null. Старый PATCH с dueDate включает FIXED, явный null снимает срок. Ответственного можно назначить по UUID участника; имя берётся из профиля. Свободные имена поддерживаются для совместимости. При отзыве доступа назначения снимаются без удаления задач. Выполнение записывается в журнал, его можно отменить. |
| Дополнение к §5.1. Папки и связанные вещи | Папки с названием и цветом, счётчики всех и выполненных задач. Задача может находиться в одной папке и ссылаться на одну вещь того же проекта. Удаление папки или вещи сохраняет задачу, очищая соответствующую связь. |
| §5.2. Коробки и содержимое (F-07–F-09) | Номер задаёт клиент, он уникален внутри проекта. Комната принадлежит тому же проекту. У вещей есть `quantity`, `firstDay` и отметки упаковки/распаковки. Batch принимает 1–100 названий (`names`) или объектов (`items`), весь список сохраняется или откатывается. Добавление, изменение количества и удаление вещи разрешены только в `PACKING`; новое количество сбрасывает отметку упаковки. Название, `lost` и `firstDay` можно менять в любом статусе. |
| §5.2. Отложенное заполнение, статусы, удаление (F-10–F-12) | Признак `contentsDeferred`, фильтрация и счётчик таких коробок; добавление вещей само не снимает признак. Пять последовательных статусов. Для `PACKED` нужна непустая коробка и отметка упаковки каждой вещи; для `UNPACKED` — отметка распаковки каждой вещи. Проверяются все записи БД, включая `lost`. В карточке и списке есть счётчики и признаки готовности с учётом статуса. Удаление коробки удаляет её содержимое. Напоминание и подтверждение удаления реализованы в мобильном приложении. |
| §5.3. Поиск (F-13–F-14) | Поиск по части названия без учёта регистра; результат содержит номер коробки, комнату и статус. Коробку можно найти по точному номеру. Для неизменных данных порядок результатов стабилен. |
| §5.4. Погрузка, доставка и прогресс (F-19–F-21) | Списки коробок с фильтрами по комнате и статусу позволяют формировать чек-лист погрузки. Отметки погрузки/доставки — переходы статусов. Сводка содержит количество по статусам и прогресс распаковки по комнатам с коробками. |
| §5.4. Первый день (F-22) | Ведётся обычными задачами со связью с вещами. При явном `includeFirstDayChecklist: true` создаются четыре задачи: зубные щётки, зарядки, чайник и постельное бельё. Старые пункты перенесены миграцией в папку «Личные задачи» с сохранением выполнения и связей. Прежний API доступен только для чтения архивного снимка; запись возвращает 410. |
| §5.4. Потерянные вещи (F-23–F-24) | Отметка `lost`, фильтр потерянных вещей и список коробок-кандидатов. Поиск кандидатов учитывает записанное содержимое и комнату, исключает распакованные коробки; это правила, не ML. |

CRUD личных наборов, применение без дублей и добровольный выбор описаны в Swagger (`/api/task-sets`).

### Папки и начальный план

- `/api/move-projects/{projectId}/task-folders`: создание, чтение, переименование, смена цвета и удаление. UUID задаёт клиент; имя — 1–80 символов после обрезки пробелов; цвета — `mint`, `cyan`, `coral`, `sand`, `lilac`, `forest`. Одинаковые названия допустимы. Повтор создания с теми же UUID и исходными данными успешен, если папка не изменена; конфликт — 409.
- Задачи фильтруются по `folderId`, этапу и выполнению. `folderId`, `assigneeId` и `linkedItemId` задаются при создании и изменении задачи; отсутствие в PATCH сохраняет значение, явный `null` очищает связь. Ответственный — создатель или участник проекта. Одна вещь может быть связана с несколькими задачами; связь не меняет её метку `firstDay`.
- Создание проекта принимает `folders` и `taskSetApplications: [{taskSetId, folderId}]`. Папка назначения должна быть объявлена в том же запросе; ошибка откатывает всё создание. Без этих полей папки и наборы не добавляются.
- Набор можно применить позднее через `PUT /api/move-projects/{projectId}/task-sets/{setId}` с необязательным `folderId`. Повтор не создаёт дубликатов; другая явно указанная папка при повторе — `409 TASK_SET_ALREADY_APPLIED`. Последующие изменения набора не меняют созданные задачи.
- Старые `taskSetIds` поддерживаются, но не совмещаются с непустым `taskSetApplications`. `includeFirstDayChecklist` устарел: отсутствие или `false` ничего не добавляет, `true` создаёт четыре обычные задачи этапа `BEFORE_MOVE` без срока в папке «Личные задачи».

Старый `GET /api/move-projects/{projectId}/first-day-checklist` читает неизменяемый архив: изменения задач, вещей и комнат на него не влияют. Перенос старых пунктов выполняется миграцией один раз; удалённые после переноса задачи не создаются заново.

### Совместная работа и архив

Относительные сроки и атомарный перенос даты переезда поддерживаются для явно выбранных невыполненных задач. Обычный PATCH проекта сроки не меняет.

Полные контракты — в [Swagger](https://hack-lead-01-ru3-vm1-3a8de1.vmaas-spirit.t-education.com/docs).

Совместные проекты доступны создателю и добавленным по почте или UUID существующим пользователям.
Подтверждение не требуется, права у всех одинаковые, включая добавление участников, архивирование,
восстановление и удаление. Список проектов включает собственные и совместные без дублей; поиск,
подсказки, чек-лист и статистика также проверяют участие. `ownerId` — только сведения о создателе.
В журнале сохраняется UUID фактического автора.
При удалении участника его назначения на задачи снимаются. Отозвать доступ создателя нельзя.

Переезд хранит nullable `archivedAt`; ответ API содержит время и вычисленный `archived`.
`PUT /api/move-projects/{projectId}/archive` архивирует на любом этапе,
`DELETE /api/move-projects/{projectId}/archive` восстанавливает. Оба возвращают 200 с проектом.
Повтор текущего состояния не меняет время и не добавляет событие. Чужой или отсутствующий проект — 404.
Архив сохраняет все данные: чтение, поиск, статистика и журнал доступны. Все изменения проекта,
комнат, коробок, вещей, задач и папок, включая переносы, статусы, коррекцию, применение шаблона,
установку/снятие связи и безвозвратное удаление проекта, возвращают 409 `DATA_CONFLICT` до восстановления.
Даже повтор изменяющего запроса в архиве запрещён; исключение — сами операции архивации/восстановления.
Устаревшие операции записи отдельного чек-листа первого дня возвращают `410 FIRST_DAY_CHECKLIST_RETIRED`, в том числе в архивном проекте.
События `PROJECT_ARCHIVED` и `PROJECT_RESTORED` содержат автора, время и UUID проекта, сохраняются
одной транзакцией с его состоянием. Список проектов принимает `archived=true/false`; отсутствие
параметра возвращает все. Фильтр применяется в БД до пагинации, включая подсчёт общего количества.

Комната хранит необязательный `iconKey` — непустой строковый ключ до 64 символов.
В создании отсутствие или `null` означает отсутствие явного выбора. В PATCH отсутствие сохраняет
значок, явный `null` очищает выбор, строка устанавливает новый. Пустая или пробельная строка и длина
больше 64 символов дают 422. Переименование сохраняет выбранный значок; старым комнатам миграция
0015 оставляет `NULL`, не определяя значок по названию.

Ключи мобильного клиента: `kitchen` — кухня, `bed` — спальня, `sofa` — гостиная, `bath` — ванная,
`book` — кабинет, `key` — прихожая, `heart` — детская, `sun` — балкон. `home` — запасной значок
для отсутствующего или неизвестного клиенту ключа. Сервер сохраняет ключ без изменения и без
закрытого перечисления, чтобы новые версии клиента могли добавлять значки.
Поле запросов/ответов комнаты называется `iconKey`, а не `icon`.

Коробки, вещи (включая поиск), подсказки поиска и сводка по комнатам
возвращают актуальный `roomIconKey` из комнаты. Старый чек-лист возвращает значок из архивного снимка.
Фильтрация коробок остаётся по `roomId`. Мобильное приложение должно отправлять выбор и читать
ключ на всех экранах, включая этикетки; изображения и fallback `home` отображает клиент.

У коробки сохраняются `title` (до 255 символов, пробелы по краям удаляются, по умолчанию `""`),
`fragile`, `firstDay` и `carryWithMe` (по умолчанию `false`). Подписи могут совпадать и не заменяют номер.
В PATCH отсутствие поля сохраняет значение, `false` снимает отметку, `title: ""` очищает подпись;
явный `null` запрещён и даёт 400, превышение длины — 422. Эти поля редактируются в любом статусе,
не меняют состав, статусы, вещи или чек-лист. `firstDay` коробки независим от одноимённого поля вещей.
`GET /api/projects/{projectId}/boxes` принимает точные фильтры `fragile`, `firstDay`, `carryWithMe`:
отсутствующий параметр не ограничивает выборку, значения `true` и `false` объединяются через И
с остальными фильтрами. Число страниц учитывает все фильтры. Поиск коробки по номеру остаётся точным;
поиск по подписи `q` пока не добавлен и требует согласования с мобильной командой.

Вещь переносится отдельным `PUT /api/move-projects/{projectId}/boxes/{sourceBoxId}/items/{itemId}/box`
с `targetBoxId`. Обе коробки должны быть в `PACKING` и принадлежать одному доступному участнику проекту.
UUID, количество, отметки и связи с задачами сохраняются. Повтор, когда вещь уже в целевой коробке,
успешен без изменения времени даже после сборки коробки; третья коробка означает конфликт 409.

Ошибочный статус исправляется отдельным `POST /api/projects/{projectId}/boxes/{boxId}/status/correction`
с `expectedStatus`, `targetStatus` и `confirmed: true`. Коррекция возвращает на любой более ранний этап,
не разрешая переходы вперёд. Несовпадение текущего статуса с ожидаемым даёт 409. Если целевой статус
уже установлен, запрос успешен без изменений времени, вещей и журнала, даже при устаревшем ожидаемом
статусе; обязательные поля и подтверждение нужны и для повтора.
Отметки `packedAt` сохраняются. Возврат в `PACKING`, `PACKED`, `LOADED` очищает `unpackedAt` всех вещей;
`UNPACKED → DELIVERED` сохраняет их и позволяет снять ошибочные отметки отдельным PATCH вещи.
Возврат в `PACKED` или `LOADED` требует непустой коробки и упаковки всех записей, включая потерянные;
иначе доступен `PACKING`. Названия, количество, `lost`, `firstDay` и связи с задачами сохраняются.
Обычный PATCH статуса по-прежнему принимает только следующий этап или повтор текущего.
Событие `BOX_STATUS_CORRECTED` содержит автора, время, `previousStatus` и `newStatus`; у остальных
видов событий эти поля `null`. Клиент должен показать подтверждение с последствиями для распаковки.

## Надёжность и ограничения — ТЗ §8

- **Пароль:** от 1 символа при регистрации и смене пароля. Пустые строки и строки только из пробелов отклоняются; пароль хранится в виде хеша.
- **Доступ:** текущий пользователь определяется из JWT. Создатель и добавленные участники имеют равные права в конкретном проекте. Остальные проекты этих пользователей остаются недоступны.
- **Целостность:** ограничения БД защищают номера коробок и названия комнат внутри проекта; изменение данных и запись события выполняются одной транзакцией.
- **Повторы:** повтор текущего статуса коробки или отметки выполнения не создаёт дополнительного события и не меняет время.
- **Длинные списки:** общая пагинация `page/size`, размер до 100, фильтры. Есть проверки пакетной записи и удаления больших наборов; измерений задержки под нагрузкой пока нет.
- **Хранение:** данные сохраняются в PostgreSQL при обновлении страницы и перезапуске приложения. Схема обновляется миграциями Liquibase; Hibernate использует `ddl-auto=validate`.
- **Наблюдаемость:** журнал создания проектов/коробок, смены статусов и выполнения задач; readiness проверяет в том числе БД. Технические метрики API, JVM, пула соединений и LLM доступны для сбора Sage через защищённый endpoint.
- **Локальные справочники:** шаблоны задач и базовый первый день не требуют сторонних сервисов.
- **ML-опись:** фотография передаётся внешнему LLM Proxy и провайдеру модели по запросу авторизованного пользователя. При отсутствии ключа или недоступности LLM распознавание возвращает ошибку; остальные функции не требуют LLM.
- **Лимит ML:** по умолчанию 15 запросов за скользящие 60 секунд на пользователя суммарно по всем ML-сценариям. Превышение — `429 ML_RATE_LIMIT_EXCEEDED` с `Retry-After`. Параметры: `ML_RATE_LIMIT_MAX_REQUESTS`, `ML_RATE_LIMIT_WINDOW_SECONDS`; счётчик хранится в памяти одного экземпляра backend.

## Дополнительные ML-возможности — ТЗ §6

| Возможность | Реализация backend |
| --- | --- |
| Описание одного предмета по фото | `POST /api/ml/item-description` возвращает название главного предмета и предложенные метки. |
| Опись нескольких вещей по фото | `POST /api/ml/items-description` возвращает `items`: 1–100 уверенно распознанных предметов с индивидуальными метками. Одинаковые предметы представлены отдельными элементами; порядок модели сохраняется, поля количества нет. |
| Сверка распакованных вещей с описью | `POST /api/move-projects/{projectId}/ml/boxes/{boxId}/unpacking-verification`: одно фото сравнивается с текущей описью выбранной коробки из 1–100 вещей. Возвращаются `matched`, `notSeen` и `unmatched`. |
| Планирование упаковки комнаты | `POST /api/ml/room-packing-plan` принимает описание комнаты и/или фото и возвращает количество коробок, распределение вещей, порядок упаковки и кандидатов на отдачу/утилизацию. |
| Проверка и сохранение результата | Пользователь может исправить название и метки `fragile`, `first_day`, `carry_personally`, затем сохранить выбранные вещи существующим API. Распознавание само не заполняет коробку; метки доступны для редактирования и возвращаются при чтении и поиске вещей. |

Маршруты распознавания и сверки требуют JWT и принимают одну фотографию JPEG, PNG или WebP
до 10 МиБ. Фото и результаты распознавания отдельно не сохраняются. Полнота описи и точный
подсчёт вещей не гарантируются.

Распознавание одного предмета и списка не требует проекта и не обращается к БД проекта.
Прежние маршруты `/api/move-projects/{projectId}/ml/item-description` и
`/api/move-projects/{projectId}/ml/items-description` удалены; клиентам нужно перейти на `/api/ml/...`.
Сверка распаковки требует JWT владельца или участника проекта и сохраняет маршрут с `projectId` и `boxId`.

Сверка доступна при любом статусе коробки. Backend проверяет доступ к проекту и принадлежность
коробки проекту, фиксирует опись в короткой read-only транзакции и завершает её до вызова LLM.
В LLM передаются фото и названия вещей с идентификаторами. Пустая опись возвращает
`422 EMPTY_INVENTORY`, более 100 вещей — `422 INVENTORY_TOO_LARGE`; список не обрезается.
Сопоставление учитывает смысл названий и видимые признаки. Каждый видимый предмет
соответствует максимум одной записи; одинаковые экземпляры учитываются отдельно, в порядке описи.
Неоднозначное соответствие остаётся в `unmatched`. `notSeen` означает «не обнаружено на этом
фото», а не подтверждённую потерю; `unmatched` не доказывает, что вещь лишняя.
Отчёт содержит `boxId`, `matched: [{itemId, name, photoDescription}]`,
`notSeen: [{itemId, name}]`, `unmatched: [название]`.
Отчёт не сохраняется, статусы и отметки `lost` не меняются. Изменения описи во время
ожидания LLM в отчёт не входят. При нераспознаваемом фото возвращается
`422 IMAGE_NOT_RECOGNIZED`. Чужие/повторные идентификаторы и некорректный ответ модели
отклоняются с `502 LLM_INVALID_RESPONSE`. Ожидание до 120 секунд, рекомендуемый таймаут
мобильного клиента — 150 секунд. Оценка повреждений и сравнение с исходным фото не выполняются.

### Планирование упаковки комнаты

`POST /api/ml/room-packing-plan` требует JWT; проект и комната в БД не нужны.
Два формата запроса:

- `application/json`: `{"description":"Кухня: посуда, книги и чайник; чайник нужен в первый день"}`.
- `multipart/form-data`: одно фото `photo` (JPEG/PNG/WebP до 10 МиБ), текстовое поле
  `description` или оба источника. Описание — до 4000 символов после удаления крайних пробелов.

Нужен хотя бы один источник. Пустое описание без фото — `422 ROOM_INPUT_REQUIRED`,
превышение длины — `422 DESCRIPTION_TOO_LONG`. Пустой или неверный файл отклоняется
существующим валидатором фото, даже если есть текст. Повторные и неизвестные multipart-поля
отклоняются с `400 INVALID_MULTIPART`.

Ответ содержит `boxCount`, `boxGroups: [{label, count, items, packingAdvice}]`,
упорядоченный `packingOrder`, `declutteringSuggestions: [{item, action, reason}]`
и `assumptions`. `action` — `donate` или `discard`; список кандидатов может быть пустым.
Каждый список содержит не более 100 элементов. Общий `boxCount` вычисляет backend как
сумму положительных целых `count` групп, максимум 100 коробок. Названия ограничены
255 символами, пояснения — 1000. Для успешного плана группы, вещи каждой группы,
порядок действий и допущения непустые.

Количество приблизительное: основа оценки — коробки около 40 × 30 × 30 см с ориентиром
загрузки до 10 кг; модель указывает это в `assumptions`. Тяжёлое и хрупкое разделяются,
вещи первого дня упаковываются последними и отдельно. Крупная мебель и техника
описываются в подготовительных действиях, а не как содержимое обычных коробок.
Текст может уточнять невидимые на фотографии вещи. Скрытые предметы, точный вес и размеры
по фотографии не определяются. Кандидаты на отдачу/утилизацию требуют проверки пользователем;
внешний вид сам по себе не означает, что вещь не нужна.

Текст и/или фото отправляются внешнему LLM Proxy одним запросом. Они и план отдельно
не сохраняются, коробки и вещи не создаются. Ожидание до 120 секунд, рекомендуемый таймаут
клиента — 150 секунд. Недостаточные данные или отказ модели — `422 ROOM_PLAN_NOT_GENERATED`;
невалидный ответ — `502 LLM_INVALID_RESPONSE`; недоступность/перегрузка — `503`, таймаут — `504`.
Ответ прокси ограничен 64 КиБ. Оценка качества на реальных комнатах выполняется отдельно.
Генерация персональных чек-листов пока не реализована.

## Дополнительные возможности — мониторинг Sage и Grafana

Для наблюдения за работой используются Sage и Grafana. Backend публикует технические метрики через Spring Boot Actuator 
и Micrometer, Sage собирает их, а Grafana отображает на дашбордах. 
Это позволяет отслеживать нагрузку, задержки, ошибки API, потребление памяти и технические сбои при обращении к LLM 

### Сбор метрик

Метрики доступны через `GET /actuator/prometheus`. Endpoint защищён отдельным токеном `METRICS_SCRAPE_TOKEN`, который передаётся в заголовке:
Настройка сбора в Sage и дашбордов Grafana выполняется отдельно от деплоя бекенда.

### Метрики в Grafana

На текущий момент в Grafana представлены следующие показатели:

| Показатель                    | Что показывает                                                                                                                          | Для чего используется                                                                                         |
|-------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------|
| Доступность сбора             | Успешность получения метрик с backend: `up = 1` — сбор успешен, `up = 0` — неуспешен.                                                   | Позволяет заметить потерю связи с приложением или проблему со сбором метрик.                                  |
| Нагрузка API (RPS)            | Количество HTTP-запросов в секунду.                                                                                                     | Помогает оценивать интенсивность обращений и сопоставлять рост нагрузки с задержками и ошибками.              |
| Серверные ошибки API          | Ответы API с кодами `5xx`.                                                                                                              | Позволяет обнаруживать сбои обработки запросов и оценивать их динамику.                                       |
| Использование памяти JVM      | Объём памяти, используемой Java-приложением.                                                                                            | Помогает отслеживать потребление ресурсов и выявлять устойчивый рост использования памяти.                    |
| Технические сбои LLM          | Неуспешные технические исходы LLM-операций, включая таймауты, недоступность, ошибки внешнего сервиса, некорректные ответы и перегрузку. | Позволяет отдельно наблюдать за надёжностью ML-функций.                                                       |
| Время ответа p95 по маршрутам | 95-й перцентиль длительности HTTP-запросов с разбивкой по маршрутам.                                                                    | Помогает находить медленные маршруты: около 95% измеренных запросов выполняются не дольше указанного времени. |


Доступность сбора метрик не заменяет проверку готовности приложения. Для неё используется `GET /actuator/health/readiness`, который учитывает подключение к PostgreSQL.

Технический успех LLM-операции не гарантирует правильность распознавания предметов или качество рекомендаций. Ответ о невозможности распознать изображение также следует отличать от технического сбоя.

## Реализовано в мобильном приложении

| Часть ТЗ | Реализация |
| --- | --- |
| §5.2. Напоминание об отложенном содержимом | Реализовано в мобильном приложении; backend хранит признак `contentsDeferred` и позволяет фильтровать коробки по нему. |
| §5.2. Подтверждение удаления | Мобильное приложение показывает подтверждение перед запросом удаления к API. |
| §5.3. QR, этикетка, печать/PDF и показ на телефоне (F-15–F-18) | Генерация и отображение этикеток, сканирование QR и печать реализованы в мобильном приложении. Backend возвращает существующую коробку по UUID. |
| §5.5. Три локальные памятки (F-25–F-27) | Памятки об упаковке хрупкого, перевозке документов и ценностей, вещах для упаковки в последнюю очередь реализованы в мобильном приложении. |

Метки вещи `fragile`, `first_day`, `carry_personally` возвращаются в `flags`.
Для совместимости `firstDay` остаётся вторым представлением того же признака первого дня.
В PATCH `flags: []` снимает все метки; `firstDay: false` снимает
только этот признак. Связи задач с вещью от этих полей не зависят. Противоречие двух явно переданных представлений — 422,
весь запрос, включая batch, отклоняется без частичных изменений.
